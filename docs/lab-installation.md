# Lab installation

A lab is an ordinary Vorteo installation that you use to develop Vorteo itself. Development installs there as often as it likes, so its restarts never interrupt the installation you use for other work, which this guide calls production. Production upgrades only to revisions you choose after the lab has run them. Anyone can run this pattern: the lab gets no privileges, credentials or endpoints that a fresh installation would not have, and production trusts nothing from the lab except a Git revision you choose.

Use a second machine for the lab. A second installation in the same account on the production machine could read production's credentials, and it would share production's Docker engine, Tailscale node and launchd session, which are the parts lab changes most often restart.

Any installation can modify itself: its Builds thread integrates and installs the change locally, then pushes it or opens a pull request. A lab is an installation you use that way for Vorteo. Production instead updates to a revision you choose from the repository. Status: this guide covers setting up the lab. Updating an installation from a chosen tag or `main` revision is planned and not implemented; today updates arrive as source an agent submits.

## Separation

The lab is a new installation, not a copy. It gets its own:

- installation ID, owner password, coordinator and daemon identities, all generated by the installers
- Tailscale names: the lab Mac's own node for the Host and coordinator, and a new generated node for its Dev container
- state, releases, logs and Projects folder
- provider accounts, connected through the lab's interface

Never copy production state, credentials, `coordinator.json`, `installation.json`, provider sign-ins or browser storage into the lab. Never give lab agents a production credential. Never point a custom domain or `redirectOrigins` entry for production at the lab.

Lab Host agents run as the macOS account that installed the lab, like any installation's Host agents. Installing in the account you use for other work on that Mac is supported and lets the lab run in the background, but those agents can read that account's files and credentials. Leave desktop automation unavailable on a Mac you are using.

Both installations can share one tailnet. Their names differ because they run on different nodes, so the default ports do not collide.

## Prerequisites

On the lab Mac, signed in to the macOS account that will own the lab:

- Docker with Compose, running. `docker info` succeeds.
- Tailscale, signed in to your tailnet, with MagicDNS and HTTPS certificates enabled. `tailscale status --json` reports `BackendState` `Running`.
- Node 24 and npm at a path that will not change on upgrade, such as an nvm-managed version, plus Git 2.38 or newer. The Host LaunchAgents run the exact Node executable that ran the installer.
- Enough free disk for an image build and a release build. Record free space before and after.

Run a preflight before changing anything, and record the results privately:

- `ls ~/Library/LaunchAgents | grep local.vorteo` and `docker ps -a` show no other Vorteo installation, or you have chosen paths and ports that avoid it.
- `tailscale serve status --json` does not use the HTTPS ports you plan to use.
- `lsof -nP -iTCP -sTCP:LISTEN` shows the loopback ports free.

## Choose paths

Keep every lab path outside the source checkout, outside the Projects folder and outside any writable Docker bind mount. The installers refuse paths that break these rules.

| Purpose                    | Example                               |
| -------------------------- | ------------------------------------- |
| Source checkout            | `~/.local/share/vorteo-lab/source`    |
| Container deployment       | `~/.local/share/vorteo-lab/container` |
| Host installation root     | `~/.local/share/vorteo-lab/host`      |
| Private installer inputs   | `~/.local/share/vorteo-lab/private`   |
| Projects folder (lab-only) | `~/vorteo-lab-projects`               |

Use a lab-only Projects folder. Lab Dev agents can write everything in it, so do not point it at a folder that holds your other projects.

## Install

1. **Check out reviewed source.** Clone the repository into the source checkout and check out the reviewed commit you are installing. Record its full SHA.
2. **Install the Dev container.** From the checkout:

   ```sh
   mkdir -p ~/vorteo-lab-projects
   PASEO_PROJECTS_FOLDER="$HOME/vorteo-lab-projects" PASEO_HOST_LOOPBACK_PORT=6768 \
     ./docker/multiplex/install.sh ~/.local/share/vorteo-lab/container
   ```

   `PASEO_HOST_LOOPBACK_PORT` publishes the container daemon on host loopback only, which the Host extension needs. Complete the Tailscale login the installer prints. It prints the container's HTTPS origin when ready.

3. **Collect the container values.** The Compose project is the generated `PASEO_INSTANCE` in the deployment's `.env`; the container is named `<instance>-paseo-1`. Read the daemon identity with `docker exec --user paseo <container> cat /home/paseo/.paseo/server-id`. Copy only the `PASEO_PASSWORD` value into a private file, mode `0600`, under the private inputs folder. The Host installation root must still be empty, so do not put it there.
4. **Write the Host plan** in the private inputs folder. See [setup on the host](execution-installation.md#setup-on-the-host) for every field.

   ```json
   {
     "root": "/Users/<you>/.local/share/vorteo-lab/host",
     "revision": "<full reviewed SHA>",
     "containerName": "<instance>-paseo-1",
     "containerServerId": "<server-id from step 3>",
     "containerDaemonHome": "/home/paseo/.paseo",
     "containerPasswordFile": "/Users/<you>/.local/share/vorteo-lab/private/container-password",
     "containerOrigin": "https://<instance>.<tailnet>.ts.net",
     "projectsFolder": "/Users/<you>/vorteo-lab-projects",
     "containerPort": 6768,
     "docker": "<absolute path from command -v docker>",
     "tailscale": "<absolute path to the Tailscale CLI>"
   }
   ```

5. **Install the Host extension** with the stable Node executable, from the source checkout:

   ```sh
   node scripts/install-execution-host.mjs install --plan ~/.local/share/vorteo-lab/private/host-plan.json
   ```

   It prints the lab's protected HTTPS origin and the owner password file.

6. **Sign in and connect accounts.** Open the origin, choose Connect to Host and enter the lab owner password. Connect provider accounts in the lab interface.

## Acceptance

Record pass, fail or not tested for each check, with the installed revision.

- `node scripts/install-execution-host.mjs status --root <host root>` reports both services registered and ready.
- The lab's installation ID, origin and both daemon identities differ from production's. Searching the lab's private files for production's installation ID, origin and Host node name finds nothing.
- The lab interface opens from a phone and a workstation, signs in with the lab owner password, and lists Dev container and Host.
- One agent in Dev and one on Host complete a real model call with a lab-connected account.
- A Host restart requested from a lab agent appears only in the lab's Installation controls, and completes after you approve it there.
- Production stays healthy throughout: its status, interface and running agents are unaffected.
- Desktop permissions are tested or recorded as intentionally unavailable, per [macOS desktop permissions](execution-installation.md#macos-desktop-permissions).

## Rollback and removal

Each step leaves the previous ones intact, so roll back in reverse order.

1. **Host extension.** `node scripts/install-execution-host.mjs remove --root <host root>` stops the two lab services, disables their LaunchAgents and removes their HTTPS routes. It keeps state, credentials and the record for diagnosis. A failed install leaves its record in the root; inspect the logs, run `remove`, and install again into a new empty root rather than deleting state to force a retry.
2. **Dev container.** From the deployment folder, `docker compose --project-directory . --env-file .env -f compose.yaml -f projects-folder.compose.json -f host-loopback.compose.json down` stops and removes the container. Its state stays in the deployment folder and the `<instance>-tailscale` volume.
3. **Permanent removal**, after you have kept anything you want: delete the Host root, the disabled LaunchAgent files inside it, the container deployment folder, the `<instance>-tailscale` volume and the lab image. Remove both lab Tailscale serve routes if any remain, and remove the container's node from the Tailscale admin console. The lab Projects folder is yours to keep or delete.

Removal never touches production, because no lab path, service, route or credential is shared with it.
