# Host and container execution

The optional macOS installation extension adds a native host daemon and a protected web interface beside an existing Docker installation. Docker continues to run the development container. Apple Container and Linux host setup are separate [future projects](plans/execution-environments/README.md).

This implementation requires host installation and acceptance. Source checks alone do not establish that an installation is running or usable from a phone.

## Use the installation

Open the private HTTPS address returned by setup. Choose Connect to Host on the welcome page, enter the owner password generated by setup, then select Connect. Closing that dialog discards the password draft and any sign-in error. Create New installation shows the setup command; Demo opens isolated sample workspaces. The interface registers **Dev container** and **Host: full account access** together. New work defaults to the container. Selecting the host requires confirmation. Local versus new worktree remains a separate choice within the selected environment. Any project can contain workspaces from both environments, including workspaces that use different repositories. Each environment resolves its own directory and retains its own agents and credentials.

New tasks choose **Environment**, **Account** and **Profile** together in the composer chooser. Desktop shows three columns; compact layouts use expandable sections. Project and isolation controls stay above the composer, without a separate environment dropdown. Switching environments keeps the draft text and attachments. Tasks created in Host and Dev container stay in the same visible workspace, with an environment label on each task tab. The app maps the workspace's exact folder through configured shared roots, preserving worktree paths. If no mapping exists, choose the folder once in the destination environment; later tasks in that workspace reuse it. Selecting an environment creates nothing until you start the task. Updated destination daemons must advertise `workspaceTaskEnvironments`.

Uploaded files transfer when the task starts. Workspace file references and plugin attachments require removal or a return to their original environment before submission. A failed connection or transfer leaves the draft intact. Continuing an existing conversation in another environment remains a separate reviewed handoff with a destination folder. Moving a workspace to another project preserves its history, files and execution environment; use **Move to project** in its menu or drag it onto the project on web and desktop. Project moves require the daemon's `workspaceProjectMembership` capability.

For an existing browser or PWA entry point, publish an installation redirect to its existing web directory with the [guarded web publisher](instance-continuity.md#publish-a-web-only-change). Add `--installation-origin <protected-https-origin>` to the build command. The entry keeps the current path, query and fragment, then replaces the page with the protected interface. Existing bookmarks and reloads reach the installation without remembering a second address. Daemon API and WebSocket endpoints stay in place; no daemon restart is needed. The release receipt records the redirect destination.

Before changing that entry, verify the actual window's origin, version and connection profiles, and back up its browser storage and current web release. Local preferences and unsent drafts belong to their original origin. Preserve them and migrate only reviewed UI data when needed; never copy host credentials into the old origin or import guest connection/plugin configuration as host authority. Existing conversations, workspaces and provider profiles remain on their daemon. Check for an old service worker that could intercept reloads. A packaged desktop app loads its own bundled scheme, so changing a web entry alone does not configure a desktop launcher. Verify the actual launch and reload flow before declaring that client integrated.

Host agents run as the signed-in macOS account. They can access its files, provider credentials and administrative tools to the same extent as an agent launched directly by that account. This is an intentional trust choice, not a stronger sandbox. macOS permission prompts still apply. Provider accounts remain local to their environment.

Settings → General has **Prepare host update task** and **Prepare host merge task**. Each opens a separate editable draft targeting this installation's host. Review the message, select the source project and agent preset, then send it. Clicking the settings action does not create an agent, merge code, deploy or authorize a restart. Without a connected installation host, the action reports that prerequisite instead of choosing another environment.

The trusted installation interface disables agent browser automation and rejects client plugin bundles from the container or any unrecognized daemon. Client plugins from the explicitly configured native host remain trusted. This restriction protects the host credentials held by the installation interface. Ordinary interfaces retain their existing behavior.

### Browser tools for Host agents

Host agents get browser tools from a disposable headless Chromium instead of the installation interface. Enable the daemon-owned host in the Host daemon's `config.json`:

```json
{
  "daemon": {
    "browserTools": {
      "enabled": true,
      "headlessHost": {
        "enabled": true,
        "deniedOrigins": ["https://<protected-interface-origin>"],
        "allowedHosts": ["localhost:8081"]
      }
    }
  }
}
```

The daemon reads `headlessHost` at startup, so a change needs a daemon restart. Older daemons ignore the setting. For the Dev daemon, see [Browser tools for Dev container agents](#browser-tools-for-dev-container-agents). An invalid `allowedHosts` entry, an unknown `headlessHost` key such as a misspelled `deniedOrigins`, or a value of the wrong type stops the browser host from starting rather than loosening its policy; the daemon itself still starts and logs the error. Older daemons, including Host releases before `vorteo.736`, refuse to start on an invalid `headlessHost` entry, so check the JSON before restarting one.

Chromium never runs inside the daemon. On the first browser request the daemon starts a separate browser host process and talks to it over Node IPC. After a crash, browser requests fail fast while a backoff of 1 to 30 seconds runs, then the next request starts a new process; open tabs are lost. The daemon stops the process when it shuts down. `paseo browser host` uses the same process, so the CLI never loads Playwright either.

That process entry, `headless-host-process.js`, is deliberately outside the initial Host module contract. That contract covers the daemon worker, CLI and other startup entries, and a test checks that their traces never reach Playwright.

To run a host without a restart, start it as the macOS account that runs the Host daemon:

```sh
paseo browser host --deny-origin https://<protected-interface-origin> --allow-host localhost:8081
```

The browser host process receives only `PATH`, `HOME`, `TMPDIR`, locale and `PLAYWRIGHT_BROWSERS_PATH` from its parent; SSH agent sockets, provider tokens and other variables stay behind. Each side validates every IPC message and drops malformed ones, so a misbehaving browser process cannot crash the daemon.

The command connects only to the local daemon through its local credential and refuses `--host`. Both forms register as `headless chromium`; the Settings → Agents **Browser tools** switch still decides whether agents receive the tools. Each run starts with an empty in-memory profile, with no cookies, storage or saved logins from any owner interface. Downloads are refused, service workers are blocked and each tab is visible only to agents in the workspace that opened it. Popups join their opener's workspace.

The browser cannot reach this machine or private networks by default. Every request, including loopback, goes through a filtering proxy inside the browser host process. The proxy resolves each name itself, refuses private destinations and connects to the exact address it checked, so redirects and DNS rebinding cannot reach a refused address. It refuses:

- loopback, link-local, private (RFC 1918), CGNAT and Tailscale (`100.64.0.0/10`) and other reserved IPv4 ranges
- IPv6 loopback, link-local, unique local (including Tailscale) and multicast addresses; IPv4-mapped, IPv4-compatible and NAT64 (`64:ff9b::/96`) forms of refused IPv4 addresses; and all 6to4 (`2002::/16`) and Teredo (`2001::/32`) addresses
- `localhost`, single-label names, and names ending in `.localhost`, `.local`, `.internal`, `.home.arpa` or `.ts.net`
- any public name that resolves to one of those addresses

WebRTC cannot send UDP outside the proxy. `allowedHosts` and `--allow-host` open a specific private destination, as `host`, `host:port` or a port range `host:first-last`; use them for a local preview server, never for the protected interface or daemon ports. A range such as `<preview-host>.ts.net:32768-32799` covers the managed preview ports on one name without opening the host's other services, so new previews need no configuration change or restart.

`deniedOrigins` and `--deny-origin` block a host on every scheme and port, even when it is also allowed. They apply to navigation, redirects, popups, frames, fetches and WebSockets. Always deny the protected interface and any `redirectOrigins`. Host agents can already read owner-account files, so this guard limits accidents and prompt injection; it does not contain a hostile Host agent. Never register a Host-side browser host, including `paseo browser host` run on the Mac, with the Dev container daemon. Guest agents could then use a browser on the host network.

To capture Vorteo itself, point the browser at an isolated preview or the e2e harness daemon and Metro server, never the protected interface. `--viewport 390x844` starts tabs at phone size, and `browser_resize` changes one tab. Use `--headed` to watch the browser. The command needs `playwright-core` and a Playwright Chromium build; run `npm run browser:setup` in the checkout when they are missing. Chromium comes from the account's Playwright cache, outside release custody: release installation neither pins nor verifies that executable. The command stops when its process exits and reconnects after daemon restarts.

### Browser tools for Dev container agents

The Dev daemon can run its own headless browser with the same `headlessHost` settings in its `config.json`. Chromium then runs inside the container, with the container's network and no Host access. The same private network refusal and `deniedOrigins` apply. Dev agents are less trusted than Host agents, so only enable this on a Dev build that includes the private network refusal, and deny every origin that can take owner actions: the installation origin, the Host web interface and any custom domains. Allow only the container's managed preview port range, never ports that serve Dev's own Vorteo interface or daemon. Signed-in browser profiles are never available to Dev agents.

The container needs Chromium's system libraries. Images built from the current `docker/base/Dockerfile` include them. An older running container can add them without root or a rebuild: run `npm run browser:setup` in a Vorteo checkout inside the container, as the account that runs the Dev daemon. It downloads the Debian packages into `~/.cache/paseo-browser-runtime` and wraps the Playwright Chromium launchers to use them. A container recreated from an older image loses that folder; repeat the setup. Enabling `headlessHost` takes effect at the next Dev daemon restart.

### Change the protected interface address

An owner-managed HTTPS domain can serve the full protected interface through a trusted reverse proxy. Keep the proxy configuration, TLS keys, interface files and coordinator credentials outside guest-writable mounts. Proxy to the host coordinator, preserve the canonical Host header and verify the upstream certificate. Do not serve the privileged bundle from the development container.

Set the coordinator's `public.origin` to the exact new HTTPS origin and add that origin to both daemons' explicit origin allowlists. Keep environment identities and endpoints unchanged. Restart only the coordinator to activate its configuration. Update installation and agent-client records to the new address. Back up each affected file and prepare rollback before deployment.

Optional `redirectOrigins` lists previous protected HTTPS origins. They redirect page navigation to the canonical origin, preserving paths and queries. They refuse API calls, including owner authentication. Update maintenance clients rather than sending credentials through a redirect. The new origin has separate browser storage, so authenticate there to register the existing environment connections. Preserve old storage and do not copy guest plugins, automation state or credentials into the protected interface.

## Setup on the host

Use the [host handoff workflow](host-handoff.md). The container session prepares source and validation; the host session gathers current Docker mounts, daemon identities, private networking, provider setup and service-context macOS permissions. Do not infer current deployment details from an old report.

Prerequisites are an existing container installation with an authenticated loopback endpoint, an authenticated host Tailscale installation, Node and npm, and an available signed-in macOS launchd session. The container origin allowlist must be explicit. The setup does not install Docker, Tailscale or provider accounts, and does not recreate or restart the primary container.

Prepare a private JSON plan outside Git:

```json
{
  "root": "/absolute/protected/installation",
  "revision": "FULL_REVIEWED_40_CHARACTER_GIT_SHA",
  "containerName": "existing-container",
  "containerServerId": "verified-existing-server-id",
  "containerDaemonHome": "/absolute/instance/home/inside/container",
  "containerPasswordFile": "/absolute/private/container-password",
  "containerOrigin": "https://existing-container.example.ts.net",
  "coordinatorPort": 6770,
  "hostPort": 6771,
  "containerPort": 6768,
  "httpsPort": 44444,
  "hostHttpsPort": 44445
}
```

The revision placeholder must be replaced with a reviewed commit. Ports are examples, not reserved deployment facts. Optional `docker`, `tailscale`, `containerCli` and `containerUser` fields select the existing executables and container account.

Run `node scripts/install-execution-host.mjs install --plan <private-plan.json>` in the host session. Setup archives the reviewed Git commit, builds a separate release, creates private state and credentials, adds two owned LaunchAgents, verifies application readiness and adds unused private HTTPS routes. It uses the existing container CLI to persist the trusted interface origin, reload that setting without a restart, and verify the effective allowlist. The container CLI must support `daemon config set`. Existing routes, identities, container mounts and agents are preserved.

The installer refuses protected paths exposed through any inspected writable Docker bind mount, including the Node executable and LaunchAgent files. Keep those paths outside guest mounts after installation too. It cannot prevent the owner from later weakening the machine's mount policy. Native host agents remain trusted owner-account processes and can modify owner-accessible installation files.

Keep `installation.json`, `coordinator.json`, `owner-password`, logs and generated agent client files private and outside Git. Never enter the installation password into the old container-served interface. The protected interface receives host credentials only after owner authentication; its HTML contains identities and endpoints, not passwords.

`status --root <installation-root>` reports launchd registration separately from authenticated daemon and coordinator readiness. Complete phone and workstation acceptance before describing setup as delivered.

### macOS desktop permissions

Include this check in every native host installation's acceptance. Record whether desktop automation is enabled or intentionally unavailable. Container-only installations do not need these host permissions. A working web interface and full filesystem access do not establish access to the macOS screen or application controls.

Identify the responsible executable before asking the owner to grant access. The installer writes its Node executable into the host supervisor LaunchAgent's `ProgramArguments`. Agents launched through that supervisor can be attributed to **node** by macOS, even when the child provider is inside another application's bundle. Do not choose ChatGPT, CodexCLI, Safari or the terminal from the child process name alone, and do not assume that the current shell's `node` is the installed runtime.

Inspect the installed supervisor plist and confirm attribution after a desktop permission probe. The macOS TCC log's `responsible_path` identifies the executable to show the owner; `requesting` may be a child helper instead:

```sh
plutil -extract ProgramArguments json -o - /absolute/path/to/host-supervisor.plist
/usr/bin/log show --last 5m --style compact \
  --predicate 'subsystem == "com.apple.TCC" AND eventMessage CONTAINS "AUTHREQ_ATTRIBUTION"'
```

Match the relevant request and process ancestry; unrelated applications also appear in this log. Keep the discovered path and permission evidence in the private installation record. Supply the owner with the exact executable path and the following steps:

1. Open **System Settings → Privacy & Security → Accessibility**, click **+**, then press **Command-Shift-G** in the file picker and paste the executable path. Add and enable it.
2. Repeat under **Screen & System Audio Recording** (called **Screen Recording** on some macOS versions). The entry may be named **node**.
3. If the task uses Apple Events, allow its requests to control Safari or System Events. These grants appear separately under **Privacy & Security → Automation**.

These permissions apply to the responsible executable, not an individual agent preset. The owner grants them through macOS; the installer must not edit the TCC database or disable system protections. An executable path or signing identity change can require fresh acceptance after an update.

Verify from an agent launched by the installed host supervisor, rather than an unrelated Terminal session. Check screen-capture and Accessibility permission status, capture a disposable screenshot, and read an application UI element. Remove the test capture after inspection. Record the individual results; a browser screenshot alone does not prove that native Safari or Dock capture works. With no active graphical session, leave desktop acceptance pending even if permissions are enabled.

If macOS requires the responsible service to reopen, preserve active work and use the [owner-approved restart workflow](#restart-and-recovery). Permission setup does not authorize killing or restarting the host daemon. Repeat the probes after the approved restart before marking desktop automation ready.

## Managed Dev client discovery

A paired Linux worker selected by the managed supervisor can recover a missing `VORTEO_INSTALLATION_CLIENT_CONFIG` from the existing pairing client at `~/.local/share/vorteo-installation-client/client.json`. The worker requires its persisted installation binding to identify Dev and validates that the client is a private regular file owned by its user, carries the container-only credential kind, and uses HTTPS or loopback. It rejects symlinks, malformed clients and insecure remote origins before starting. Explicit launcher configuration remains authoritative. Host and standalone workers do not discover this Dev client.

Profile and settings admission still verifies the coordinator response against the exact installation, daemon identity and environment. A missing supervisor environment variable can therefore be repaired through an approved managed worker source update. New installations should continue configuring the owned launcher explicitly.

## Restart and recovery

Both environments receive the installation-maintenance skill. Agents can submit a reason and target, then observe their request's status. They cannot approve it with their request credential. In General settings, the Installation section shows the host and dev restart requests together. Pending and running requests, coordinator updates and coordinator recoveries remain visible until they finish; history and profile sharing expand in place. Plain pending requests offer Restart when idle, Finish turns and restart, and Cancel. Queued requests offer Cancel and Restart appears stuck. Only after the operator selects Restart appears stuck does Force restart now appear, with a separate confirmation because it interrupts running work. Request cards show one short paragraph. Details contains activity, source revisions, bundle digests and submission history. Source installation is labeled Updating until it completes. New requests refresh the section without opening a dialog or moving away from the current task. A direct link to `/settings/general?installation=1` opens the same controls without restoring the last conversation. The installer generates the owner password automatically and saves it in `owner-password` inside the private installation directory on the host. The owner does not choose it during setup. Saved daemon connection credentials do not unlock these controls: owner access approves restarts and resolves shared workflow conflicts. The interface shows the exact recovery file path supplied by the coordinator. Owner access lasts seven days in the current browser and survives reloads through an HttpOnly, SameSite Strict cookie. HTTPS cookies are Secure. Select Lock controls to revoke the session immediately. The server persists token hashes, never the password or raw tokens. The password remains the initial setup and recovery credential. Native agents with full host-account access can read that file; this boundary separates container and daemon credentials from owner approval, not the owner from trusted host processes. Unlocking does not approve a restart. The owner reviews the target, reason and disruption warning and approves that exact request. Requests never expire. The plain restart queue contains at most one active request per target across all requesters and shows an empty state when no approval is pending. Later plain requests for a pending or approved plain restart return the existing request, retaining its approval and restart mode. Requests arriving after dispatch begins are refused until the restart completes. One collapsed History holds finished restarts and updates, coordinator updates and coordinator recoveries, including rejected, canceled and completed receipts. Finished recoveries show their outcome and time, with the full plan behind Exact recovery details.

Restart links use `/settings/general?installation=1&restart=<request-id>`. They focus the exact request after owner unlock while keeping both targets visible. Opening the link never approves it. Rejected, superseded and missing requests cannot authorize another request. The installed maintenance client returns `approvalUrl` from request and status commands; the host client uses its configured public origin for browser links while keeping authenticated requests on loopback.

Host installations can configure `host.startupValidation` with the protected Node executable, supervisor entrypoint and daemon home. Before either immediate or idle dispatch, the coordinator runs that exact entrypoint in validation mode. Invalid configuration or an unavailable release blocks dispatch and leaves the running daemon alone. Validation does not initialize state, acquire a PID lock or launch a worker. Failure receipts identify invalid field paths without copying configuration values.

Point the service and validation entrypoint at the same complete release. An older bootstrap that validates configuration before importing a newer supervisor can reject settings that the new runtime accepts. Disabled provider markers remain disabled under the current schema. The owned launchd service retries transient startup failures. Persistent configuration or release failures require repair rather than repeated disruptive restarts. A timeout receipt explains whether Host configuration validation still passes and identifies the service log and recovery checks. No automatic rollback of databases, provider credentials or owner settings is attempted.

Finish turns and restart blocks active goals without interrupting the current turn. Confirmed goal holds survive a daemon restart even when the task has no queued messages. Threads without goals that receive the finish warning retain a durable continuation message. Both Host and Dev restore this work after the hold ends; manually paused goals and queues remain paused. New goal activation is refused during the hold, and failed goal blocks prevent restart readiness.

The coordinator persists approval and running state before dispatch. It runs one restart at a time and reports success only after reconnecting to the expected daemon identity and observing a replacement worker. Connection and status checks allow up to 30 seconds for healthy daemons whose provider probes are slow. Container-daemon restart uses the existing supervisor and retains the container. Native host restart uses only the installation-owned launchd service. The coordinator is a separate service and survives either restart.

Requested and queued restarts appear in a persistent banner at the bottom of the sidebar. Review the target and short reason in Settings. Queued restarts show elapsed waiting time and activity counts. The sidebar offers Review restart; force escalation is available only in the queued request’s settings. If owner controls are locked, the banner shows counts and links to unlock; task identities and reasons remain protected.

Restart when idle persists approval without an expiry and polls the target even after closing the browser. It waits on running agents, initializing sessions and provider-native workers. The daemon performs a final synchronous idle check and closes admission before restarting, so work starting after an earlier inventory causes the restart to wait again. Offline or incompatible daemons stay queued. The initial daemon upgrade still requires an ordinary owner-approved restart before this capability is available. Terminals may disconnect even during an idle restart. Cancel withdraws approval before dispatch.

A queued plain restart authorizes restarting the installed runtime at the selected time. Later plain requests share its receipt, approval and restart mode. Both scoped installation credentials can observe the receipt, but neither can approve it. This does not authorize installing different source. Use the reviewed source-update workflow below to combine code changes. Finish turns holds new agent turns, whereas Restart when idle allows them until the final idle barrier.

A coordinator restart preserves an idle approval that has not been dispatched, but marks other previously approved or running jobs as interrupted. It never replays an ambiguous restart. Inspect the target and submit a new request if another attempt is necessary. These controls do not update release files, roll back databases, or promise to preserve an in-progress provider turn.

#### Owner delegation

A Host operator can delegate routine requests with `<stateDir>/owner-delegation.json`:

```json
{
  "version": 1,
  "delegatedRequesterPrefixes": ["Nova "],
  "hostUpdateServiceRestart": true,
  "graceMinutes": 15
}
```

A missing or invalid file delegates nothing. Prefixes are display only, not authentication: approval never reads them, and they match only requests made with the Host agent credential. A Dev request that names itself the delegate still needs the owner. A delegated request appears in the sidebar and Installation controls as "Being handled by <requester>" with its reason and a Cancel action, not as an approval toast, while it is automatically approved, running, or pending for less than `graceMinutes` (default 15, at most 60). After that it returns to the normal owner prompt and toast, noting that the delegate is taking longer than expected, so a mislabeled or stalled request cannot expire unseen. Every owner decision stays available, and the locked summary counts only handled requests as queued. Coordinator update requests carry no requester yet, so they are not delegated.

`hostUpdateServiceRestart` lets an automatically approved Host source update replace the whole service, like an owner approve, instead of restarting only the worker. The update still waits out the cancellation window, prepares its candidate, holds new turns and waits for running turns to finish before the launchd restart. It keeps its exact revision and digest binding and is never replayed. The setting is part of the automatic grant's authority, so changing it cancels automatic grants that have not dispatched, and dispatch uses a full service restart only for a grant issued under the current setting. Standing interruptions and Dev updates keep their existing restart paths.

#### Rolling the coordinator back to vorteo.689

Vorteo.689 reads `<stateDir>/restart-jobs.json` with a strict schema that predates `continuationCaptureId`. Later coordinators record that field only while a Restart when idle request holds a task capture, remove it when the hold is released, and never send it to clients. A job keeps it only in a short window: between capture and the idle check, or while the target is unreachable and the release keeps failing. A rollback during that window makes vorteo.689's startup fence reject the journal.

Before rolling back, cancel or finish every approved Restart when idle request, then confirm that no job in `restart-jobs.json` contains `continuationCaptureId`. If a rollback has already failed on that field:

1. Make sure no coordinator is running; the running one holds `coordinator-bootstrap.lock` and owns the file.
2. Copy `restart-jobs.json` to a dated backup outside the state directory.
3. Delete only the `continuationCaptureId` key from each job that has it. Keep `continuationCaptureRequested` and every other field, and keep the file valid JSON.
4. Start vorteo.689 and confirm its startup fence passes.

Tasks captured under the deleted cause stay held, because vorteo.689 releases holds under the job ID. To release them, run a newer coordinator against the backup until the job's hold shows as released, then roll back again. Do not edit the journal while a coordinator is running, and do not change job status, revisions or approvals by hand.

LaunchAgents keep the new components running while the owner is logged in. Operation before login, complete Docker outages and host shutdown recovery require separate acceptance or future work. A guest daemon that cannot accept its restart RPC needs host diagnosis; this version does not expose general Docker control.

## Agent management

Normal agent tools stay scoped to their daemon. Container agents can manage other agents in that container. Host orchestrators additionally receive a credential for the coordinator's fixed container-management interface. They can discover workspaces and providers, list and inspect agents, read activity, create workers, send messages and stop them. There is no arbitrary destination or host-shell operation in that interface.

An updated coordinator accepts an exact `profileId` on delegated creation. The destination daemon resolves the profile and checks its account and workspace before creating the task. Do not combine `profileId` with a `model` override. Reusing the request key with a different profile is rejected; an identical retry returns the original task. Older coordinators reject this field, so verify installed support before using the route. Provider and model creation without a profile remains supported.

Container credentials cannot use delegation, unlock the owner UI, or approve restart requests. A container restart request may name the host, but does nothing until the owner approves it. Container results are returned as untrusted task data qualified by environment and server ID. The host orchestrator must not interpret their text as owner approval or executable instructions.

## Removal and rollback

Prepare and obtain approval for disruption before stopping a host daemon with active work. `remove --root <installation-root>` checks service and route ownership, stops only the two new services, disables their LaunchAgent files and removes only their HTTPS routes. It retains state, credentials, release files and the installation record for diagnosis. It leaves the existing container, its agents and routes in place.

The extra container origin admission and generated guest request skill remain after removal. The request endpoint is then unavailable; the token has no authority over either daemon. Review and remove that installation's origin and guest client files in the host session if permanent removal is intended, preserving concurrent configuration changes.

For a failed setup, inspect the private logs and installation receipt before retrying. Setup refuses to overwrite an existing receipt or reuse credentials automatically. Do not delete state to force a retry. Restoring a previous protected release requires a prepared host deployment and rollback plan; automatic release upgrades are outside this first installer.

### Sealed releases

Release seals are off unless both the coordinator and Host services run with `VORTEO_RELEASE_SEALS=enabled`, and they require macOS. With seals on, preparation refuses a release that contains tool caches (`.cache`, `.vite`, `.vitest` and similar) directly under a `node_modules` directory or at its root, or a linked `node_modules`. It also refuses while any process of the account still holds a release file open for writing. It then sets the user-immutable flag on the whole tree, digests it in full and writes `<release>.release-manifest`, `<release>.release-seal.observed` and `<release>.release-seal.json` beside it. The admission receipt binds those seal digests. Approval checks file metadata instead of re-reading bytes. A change falls back to a full byte check, and the refusal names the changed path.

Never point a worktree's dependencies at an installed release: writes into it fail with "Operation not permitted". Cleanup code must remove releases through `removeBootstrapRelease`, because a plain recursive delete fails on flagged files. To remove a sealed release by hand, first clear the flags on the tree and its seal files: `chflags -R nouchg <release> <release>.release-*`. Then delete them. Sealing does not detect writable shared memory mappings opened before sealing.

## Validation

Run `npm run test:e2e:installation --workspace=@getpaseo/app` for the packaged interface on desktop and phone-sized Chromium. It starts two isolated supervised daemons and the real coordinator, verifies plugin and credential boundaries, prepares both editable update drafts without starting agents, and approves and verifies a container-daemon restart. All fixture processes and state are torn down. This does not test launchd, Tailscale, macOS folder permissions or a physical phone; those belong to host acceptance.

### Finish current turns before restart

The owner can upgrade a pending or queued restart to finish current turns. The
coordinator journals approval before asking the target daemon to hold new work.
The daemon blocks new starts, holds queued delivery and scheduled dispatch, and
uses the existing durable goal hold to pause automatic continuation without
interrupting a running turn. Active threads receive a timeline warning; providers
with steering also receive the instruction during their current turn. Unsupported
providers finish normally. No timeout silently converts this into a forced restart.

The existing idle check includes provider subagents and registrations already in
flight. Before dispatch, the daemon drains persistence and saves agent snapshots.
A failed goal block remains a visible blocker. Cancellation is journaled first and
releases only the matching request's hold; a delayed canceled request cannot
reestablish it. Existing queue goal recovery preserves explicit manual pauses.
An immediate restart of a queued request requires a new explicit owner decision.
A canceled request can create a new pending request, never reuse its old approval.

The optional `gracefulRestart` daemon capability and `gracefulRestarts` installation
capability gate these actions. New owner clients request `gracefulRestarts=1` on
restart routes; older strict decoders do not receive the new journal fields.
Coordinator recovery retries approved waiting work and hold release, never an
ambiguous disruptive dispatch. A new daemon uses existing goal and queue recovery;
this does not add an independent continuation scheduler.

### Tracked Dev supervisor maintenance

A supervisor or launcher repair uses the same coordinator journal, sidebar notice and owner controls as daemon restarts. A trusted Host operator prepares a protected Node maintenance script, its SHA-256 digest and rollback procedure, then configures `container.supervisorMaintenance` with absolute `node` and `script` paths and `sha256`. A changed plan revokes undispatched automatic grants. An uncertain supervisor result blocks subsequent automatic work on Dev until a manually reviewed supervisor recovery verifies success; the failed receipt remains linked to that recovery. Coordinator automation still requires its independent recovery integration; a saved permission does not establish readiness. Helper operations remain separately reviewed.

An installation without a saved preference retains its existing trusted Host policy, if configured. The interface identifies that legacy policy until the owner saves the new preference. Migration retains explicit existing daemon permissions and starts coordinator and supervisor permissions disabled. Other installations do not gain broader automatic authority merely by installing new code. Enabling each service permission is a separate owner-authenticated setting change. An older coordinator leaves the setting unavailable with an explanation that coordinator maintenance is required. An unavailable route after support was observed is an error, not permission to reset the policy.

After a lost reply, use `coordinator-status <request-id>` before retrying the same preparation. This read-only route uses the durable ledger and returns execution and public automatic status without a Host RPC, private plans or credential bindings. The existing maintenance tick reconciles eligible coordinator requests through the native Host service. It allows one call in flight and records each attempt before connecting. Approval and dispatch validation each have a three-attempt budget. Unconfirmed calls retain their count and backoff; after a coordinator crash, a sixteen-minute observation window covers the connection and native RPC deadlines before another attempt becomes eligible. A successful approval starts a separate thirty-second cancellation interval. A launch reservation or execution receipt prevents further launches, including after a lost response. Exhausted checks require review; restarting the coordinator does not reset them. Compatible rollback releases must understand the protected attempt records before this scheduler is installed.

Capable clients request the public automatic status view. It identifies Host-policy authorization or an explicit owner decision without exposing credential bindings, signed proofs or protected retry records. Installation controls distinguish queued checks, an unconfirmed check, retry waiting, exhausted checks, the cancellation window and an unconfirmed launch. A check reservation does not prove its process is still running. Execution receipts override inferred automatic status. A reserved launch without an execution receipt calls for inspection, never another automatic launch. Older clients receive the existing request shape and retain cancellation. The displayed countdown is informative; native admission enforces the exact deadline and current authority.

Preclaim and claimed recovery reviews separately negotiate retained startup-plan support. Older clients receive original-request projections without the unknown startup field and can still cancel recovery. They cannot approve recovery while that evidence is hidden. Current clients refuse preparation against an older Host and show the original recovery service and pinned launcher in exact recovery details. Reviewing this retained evidence does not authorize another launch of the original update.

Installation controls show authorization and readiness separately for each Host or Dev requester, target daemon and operation. Automatic authority does not prove the updater is available. The versioned observation includes its check time, preference revision and selected source when available. A failed inventory, unsupported idle admission or unresolved lifecycle recovery blocks readiness.

## Trusted Host approval policy

The coordinator supports an optional protected `restartApprovalPolicy.hostRequestsAfter` timestamp. An owner-authorized installation of this policy allows authenticated Host requests created at or after that timestamp to enter the existing finish-current-turns workflow automatically. The journal records the policy timestamp, request revision and source digest before placing a hold. Installation controls and the sidebar retain progress and cancellation before dispatch. Disabling or changing the policy cancels its undispatched automatic approvals and releases their holds. Dispatched operations retain their recorded decision.

Origin comes from the scoped credential, never the requester's display name. Dev requests require owner approval, including a Host batch containing any non-superseded Dev contribution. Source must pass preparation and validation before automatic approval. Changed source cannot reuse approval. Requests older than the configured timestamp remain manual. Supervisor automation requires its separate service permission; it never inherits this legacy daemon policy. Automatic approval requires activity inspection, finish-turns holds, hold release and safe idle restart support; capabilities report whether these are available.

A Host requester can require the matching owner button by passing `--require-owner-approval` for a plain restart, source update or supervisor request. The client checks the coordinator's `requireOwnerApproval` capability before requesting or uploading anything. If support is absent, it refuses the operation. The request remains Host-originated; this option does not change credentials or installation policy. A pending shared request or source batch retains manual review if any participating contribution requires it. Replacement contributions inherit that requirement even when a repair omits the option or supplies `false`. An already approved request cannot acquire a new review requirement; cancel and prepare a new request instead.

Install a compatible coordinator and rollback reader before using this option. Legacy response projection keeps older clients readable, but it does not make older journal readers compatible with persisted approval requirements. Unresolved bootstrap generations fence lifecycle admission; they do not provide journal compatibility after a successful handoff.

This is coordinator functionality. Publishing the interface or updating a daemon does not activate it. An older coordinator without a tracked maintenance operation still needs the separately prepared, owner-approved bootstrap workflow. The [tracked coordinator bootstrap design](plans/execution-environments/coordinator-maintenance.md) specifies the first ownership transfer, authentication and acceptance gates. Never activate this policy through an untracked reload or replace a missing maintenance operation with a daemon restart.

Restart recovery resumes only work held for the restart. It must preserve queued-message identity and order, attachments and goal usage, and leave manually paused, completed or blocked work alone. Sending a new continue message to every open thread is not a recovery mechanism. Isolated queue tests cover repeated journal recovery and changed-source refusal; installation acceptance must also verify actual replacement processes and resumed work on both environments.

### Protected bootstrap runner admission

The native Host launcher may supply `VORTEO_COORDINATOR_BOOTSTRAP_SETUP` pointing to a private runner setup file. This binds the daemon ID, admission setup, complete runtime digest, fixed Node executable, runner entrypoint, lock launcher and ownership verifier. Missing or invalid setup leaves `coordinatorBootstrapReview` unadvertised. Browser requests cannot choose these paths. On macOS, a launcher that already supplies the private Host installation client can instead use its fixed sibling `coordinator-bootstrap-runner.json`. Discovery requires a private `host-agent` client and applies the same complete setup validation. This permits a tracked Host worker update to load prepared support without a separate launcher reload; discovery itself neither approves nor starts maintenance.

An exact owner approval starts the fixed runner under its inherited kernel lock. The decision response waits for acknowledgement that dispatch is durably claimed and the watchdog is armed; this does not mean installation has completed. Refresh the recorded request to observe completion or recovery. A timeout or lost response never automatically relaunches the runner. Existing approvals are not replayed when Host starts. Cancellation remains available until dispatch claims the request.

A plan with `automaticRecovery: "restore-previous"` includes one automatic rollback in the exact owner approval. Its independent native watchdog observes durable stage changes and the recorded executor's own runner activity. After three minutes without either, it signals only the recorded updater process generation, first with SIGTERM and then, if necessary after ten seconds, SIGKILL. Runner activity is diagnostic, so it can postpone this for at most 15 minutes after the watchdog starts; unreadable or foreign runner files do not count. macOS audit tokens bind signals to the PID version. Neither a recycled PID nor an observation timeout establishes ownership; restoration starts only after the updater exits and the watchdog acquires the same kernel lock.

After a failed post-unload update, the watchdog verifies the retained previous release, current selection, process identities and preserved state before restoring the coordinator. It can remove only the exact approved candidate service. A different running service or changed rollback artifacts require inspection. The receipt records rollback intent before any effect, then reports the verified result. A failed or interrupted rollback is not retried automatically. Task databases, credentials, settings and owner sessions are never restored from backups.

When the previous executable cannot read the next journal format, use `automaticRecovery: "restore-compatible"` with an exact `compatibleRecovery` release. `previous` still identifies the running process. Recovery must preserve its configuration and service settings; the plan digest binds the separate recovery source, artifact, Node, entrypoint, configuration and launcher. Older clients can read a reload notice and cancel, but cannot approve hidden recovery changes.

Compatible requests stay in `coordinator-bootstrap-pending.json` through review and dispatch claim. The executor acquires execution ownership and arms its independent watchdog before promoting the real claim into the main journal. Both journals use a persistent inode at the existing journal lock path. Its kernel lock releases on writer death; old exclusive-create writers refuse the retained inode. An existing legacy lock is never removed automatically. Promotion retains the complete claim, replaces main and fsyncs its directory before lifecycle effects. A stale sidecar cannot cancel or reclaim a promoted request; uncertain promotion requires reconciliation. Completed generations and their verified recovery ancestry remain readable without blocking later maintenance.

Startup authority reads validate the promoted records and only the exact pending recovery ancestry they reference, including related promotion evidence. A newer Host's unrelated pending plan cannot disable the current web interface just because its body adds unsupported fields. Pending envelopes and record identities remain checked; required authority is always parsed strictly. Full journal reads and new lifecycle effect writes still reject unsupported plans. This separation never strips unknown fields, rewrites stored evidence or grants authority to a pending request.

After promotion, resuming the old executable cannot establish recovery. The watchdog either verifies the approved compatible release or leaves the request unresolved. If the old process remains loaded, recovery verifies its exact identity, freezes it when necessary, checks idleness and completes missing preservation before replacement. A completed matching receipt can be reconciled; changed state, active children or an unverified process refuse restoration. Prepare and exercise the recovery executable against the full retained journal before submitting the request. Source validation does not establish installed acceptance.

After verified restoration, a new plan can name the exact failed request, revision, plan digest and execution generation in `recoveredFrom`. Admission verifies the previous updater has exited and the currently loaded service matches the restored release. The failed receipt stays intact; the new request starts pending and requires its own approval. The current callout follows the new review.

Older plans retain their original behavior and do not gain automatic recovery retroactively. Install compatible Host review support, inspector, runner and interface before preparing a plan with this field. An emergency restoration outside the installed controls requires the owner's explicit exception; it does not authorize replaying the failed update or silently changing its receipt.

This source path still requires protected installation setup and live acceptance before it is available in an existing installation.

Artifact verification accepts npm hard links only when every physical link is inside the release. It binds their paths as well as contents and rejects external aliases or changes during verification. Individually prepared executables, configuration and launcher files still require a single link.

## Native helper maintenance

The scoped Host client can submit a prepared native helper request with `request-helper --request-file <private-json-file>` and inspect its receipt with `helper-status <request-id>`. The file contains the stable request ID, reason and exact installation or rollback plan. Preserve that file when reconciling a lost response. Both commands return the exact Installation review URL. Dev credentials cannot submit or inspect these plans. Submission stays inert until the owner approves the matching revision and plan digest; the automatic Host daemon policy does not approve helper installation.

The coordinator advertises `nativeHelper.available` only to Host clients when its helper executor is configured. Protected `nativeHelper` configuration supplies the native home, Docker executable, Docker socket and immutable container ID. Each admission checks current writable mounts before accepting artifact, destination and state paths. A missing capability requires installation preparation on Host, not a direct installer invocation.

Helper receipts share the existing lifecycle journal. Legacy coordinators reject those records, including terminal history. Before enabling helper requests, prepare and verify a rollback coordinator that reads the complete journal, accepts the helper configuration schema and preserves helper recovery fences. Keep the original release and journal intact; never remove helper records to make an older coordinator start. A tracked coordinator plan can declare `nativeHelperConfiguration` to enable or replace the exact protected configuration, or `null` to disable new helper requests. Omitting it preserves existing configuration. Its digest binds the change and the review details identify it; Docker executable, socket and container identity must retain the protected Host pairing. Older bootstrap implementations reject this field. Install compatible maintenance support before submitting such a plan, and obtain its own exact approval before activation.

If compatible recovery positively identifies busy lifecycle work or active children on the exact frozen original coordinator, it may resume that process once to let work settle. Parsing, identity, preservation and ownership failures do not authorize this fallback. The durable recovery attempt remains `recovery_required`, never `resumed` or `rolled_back`. The previous coordinator is running, but maintenance remains unresolved. A new approved update is required to restore restart-safe operation. If the legacy process exits before that update, the promoted journal can prevent its restart. The owner reviews this limitation before dispatch.

Supervision recovery after a manual restoration is a separate tracked delivery path. Its optional `supervisionRecovery` plan field binds the exact canceled migration, retains the failed predecessor through `recoveredFrom`, and explicitly reviews frozen-coordinator termination. It does not claim that either earlier migration succeeded. Both the candidate and compatible recovery runtime must use a different source from the manually restored release and preserve configuration. A different source digest alone does not prove reader or executor compatibility. The original reader may ignore an unrelated new pending proposal but cannot read this field after promotion, so it must never be selected as the compatible fallback.

The dedicated review parent authenticates the owner, records the exact decision and reserves one launch under the existing lock. Its native child verifies the selected runtime, process lineage and retained plan before claiming effects. Full read-only preparation runs in a separate child with a 120-second deadline and forced termination on timeout; missing or incorrect acknowledgement refuses admission. No execution lock descriptor is inherited by that verifier. The effect path freezes only the reviewed coordinator, refuses active preparation children, preserves state, retires that exact frozen lifetime and starts the reviewed OS service. A separately pinned compatible fallback and watchdog reconcile the same generation after failure without replaying dispatch. Disposable compiled native fixtures cover successful supervision, unhealthy-candidate fallback and login registration. Those fixtures do not establish installed supervision, an actual reboot or authenticated remote workspace acceptance.

## Session host job

The coordinator owns the durable session host's launchd job, `local.vorteo.<installation id>.session-host`, on Host. It advertises `sessionHostJob.available` only to the Host client, and only when source updates select Host releases through the current link and Host startup validation is configured. Dev clients see whether the job exists, never its details. Never load, unload or edit the job with launchctl directly.

- `request-session-host --install` or `--remove` asks the coordinator for a plan; `session-host-status` reports the job, its host and the durable sessions setting, with the installed release beside the host's own release and hosted sessions by provider. The coordinator derives the plan from its own configuration: the session host entrypoint through the current link, the Host job's node, and the Host job's `HOME` and `PATH` beside `PASEO_HOME`, with no other environment.
- The owner approves the exact operation and plan digest in Installation controls. Restart decisions and the trusted Host approval policy never approve it. An approved operation waits for pending restarts and other lifecycle work, then dispatch recomputes the plan and changes nothing when it differs. A coordinator restart marks an approved or running operation failed and never replays it; check the status before requesting again.
- Install writes the plist with mode 0600 and requires the new host to answer with launchd's pid within 60 seconds and without a watchdog kill, or removes the job again. A watchdog kill during that check fails the install even though launchd starts another host. It never writes the durable sessions setting; the owner enables that separately.
- `request-session-host --restart` restarts the host on the installed release through launchd: the coordinator writes a restart marker in the session host directory, signals the running host to stop, and requires a new process to answer within 90 seconds, killing a host that ignores the stop once its command is verified. Every hosted turn running at that moment is interrupted; its worker sees the marker, waits for the new host and continues the agent there instead of starting a provider locally. The new host removes the marker; a failed restart removes it too and leaves the job loaded for launchd. The request shows how many hosted sessions the last observation found, and the owner approves it like the other operations. Clients send the operation only when `sessionHostJob.restart` is advertised.
- Hosted providers call the daemon's agent tools through the host. At open, the host replaces the daemon's injected tool server with the shipped stdio-to-socket bridge pointed at a private per-session socket under `$PASEO_HOME/session-host/tools/`, and forwards each tool message to the daemon's tool endpoint with the host's own token. While the daemon refuses connections, the host holds a message and retries for up to a minute. A notification or a read-only method is repeated after any failure, and a rejected token is held too, since it comes from a worker that has not learned the host's token yet; a tool call that fails after it may have reached a worker, whether its reply stream breaks, ends without a reply or carries a failed status, is answered at once with an error saying its outcome is unknown, so a tool never runs twice. Each request is answered exactly once from its own reply; one call's failure never touches the others in flight, a notification is never answered, and closing the provider's connection aborts its calls at the daemon. The worker strips the relay form from stored configs as it strips the direct form. A release without the bridge beside its built scripts runs hosted providers with the direct connection and logs a warning at host start.
- A host does not need a restart request to move to a newer release. Once a minute it compares its release with the one under the current link; when they differ it writes an upgrade marker, exits as soon as it runs no session, and launchd relaunches it on the installed release. Workers release hosted sessions idle for five minutes while the marker exists and wait for the returning host; running turns and pending permissions are never cut, so a host with a long turn stays until that turn ends or the owner approves a restart. The setting file accepts `idleReleaseMs` and `releaseCheckMs`; the status detail shows `upgradePending` to owner clients that declare `upgrade: true` in their query, as interfaces from release 762 do, since older interfaces parse the status strictly.
- Removal is refused while the setting is on or the host runs sessions. A host that stopped answering is stopped once the setting has stayed off past the workers' five-minute alive window, and the receipt records that forced stop. A host that refuses the connection, answers in another protocol version or never sends its session list is alive and is never stopped by force; after five minutes of that, removal fails without changes. A process that survives bootout is killed only after its command is verified as the session host.
- Host restarts and source updates never touch the job. While it is installed, source updates and supervisor maintenance refuse to select a Host release without the session host entrypoint; the lifecycle queue registers this guard whenever source updates are configured, and `install-execution-host.mjs remove` refuses to run: remove the job first. No Host release selection is automatic today. A future automatic selection must stop the job with the same forced-stop sequence rather than refuse, so a failed update cannot leave the Host down.

Session host records share the lifecycle journal. Coordinators without session host support reject that journal once such a record exists, including terminal history. After the first request, keep a coordinator with session host support as the rollback target, and never remove records to start an older coordinator.
