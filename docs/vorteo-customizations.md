# Vorteo customizations beyond Paseo

Vorteo extends Paseo with account management, reusable workflows, supervised workers and a shared Host and Dev container installation. This is the cumulative inventory of those differences, grouped by category and ordered by user impact within each category. Minor interface changes belong here rather than in the product overview.

This inventory describes the reviewed source. Availability depends on the installed client, daemon, coordinator and provider versions; source review does not establish deployment. The [roadmap](roadmap.md) tracks unfinished work, [Vorteo changelog](../VORTEO_CHANGELOG.md) records release history, and linked guides explain operation and constraints.

## Accounts and reusable workflows

- **Multiple isolated subscription accounts.** Connect separate Codex and Claude accounts, choose an account per task, and run tasks across accounts concurrently. Browser sign-in, reconnect, rename, disable and removal are account-scoped. Claude uses the official CLI login flow; account configuration, session discovery and resumed history remain isolated. This does not combine subscription allowances or automatically fail over between accounts. See [accounts and profiles](agent-presets.md) and [account isolation tests](../packages/server/src/server/agent/providers/claude/account-isolation.test.ts).
- **Reusable launch profiles.** Save model, reasoning, permissions, instructions, provider features and worker settings together. The daemon resolves the selected profile and freezes its launch configuration for the task. Later profile edits affect new tasks. Unsupported model or reasoning choices fail explicitly instead of silently selecting another model. See [launch configuration](agent-presets.md#configuration-and-compatibility) and [profile tests](../packages/server/src/server/agent/create-agent/profile.test.ts).
- **Shared workflows across accounts and environments.** Provider defaults and named workflows avoid maintaining a separate copy for each account. Managed installations keep one authoritative profile library across Host and Dev container, with explicit environment exclusions and revision checks for edits. Credentials, account connections and discovered models stay local. Profiles have an account-independent identity, retain compatible selections when switching accounts, and hide incompatible choices after catalog discovery. Legacy launch and worker references survive migration. See [profiles across execution environments](agent-presets.md#profiles-across-execution-environments).
- **Reviewed task handoffs.** Changing the profile on an existing task opens an editable context handoff and creates a successor after confirmation. The original remains accessible. Choose the destination workspace when changing environments; the project stays selected. Active managed workers must stop first. Attachments, tool results and provider-private state do not transfer automatically. See [successors and quota stops](agent-presets.md#quota-stops-and-explicit-successors).
- **Usage beside account selection.** Remaining usage, reset windows and a compact usage ring help choose an account before launching work. When a coding allowance reaches zero and prepaid credit remains, account tiles show the balance in amber with Using prepaid and retain the reset time. Cached balances are marked as last known. Reset buttons keep gray text at every quota level. Drafts restore their account and workflow together. Fresh capacity can inform successor suggestions; stale or unknown usage does not qualify as available capacity. Paseo also supplies usage discovery and plugin sources, credited below.
- **Account reset credits.** Supported providers expose account-scoped credit availability and a reviewed reset operation. Credit details include reported expiry and refresh time; redemption requires explicit confirmation and verified provider support. A confirmed reset unlocks earlier quota-exhausted threads on that provider without automatically sending a message or clearing a reserve stop. See [reset credits](agent-presets.md#account-reset-credits).
- **Local Pi endpoint visibility.** Profiles show configured model and reasoning details, private endpoint reachability and active managed-child counts. A reachable port does not prove a loaded model, valid authentication or inference capacity. Counts describe the configured provider in this daemon. See [local endpoint status](agent-presets.md#local-endpoint-status).
- **Provider management and diagnostics.** Settings groups each provider family with its accounts and shared enable controls. Reorder, remove or restore providers without deleting credentials, profiles or history; local sign-in and credential deletion remain in Manage. Account names use the same natural order across environments. Older Claude CLI versions show installed-version and model-compatibility warnings with update guidance. A separate unpublished refinement shows sign-in success and Done independently of background usage refresh.

## Goals, queues and supervised workers

- **Bounded worker teams.** A supervisor profile explicitly selects a worker account and profile, including cross-provider delegation, and limits concurrent managed workers, including Pi workers using local or private OpenAI-compatible endpoints. Existing teams retain their account binding until edited; new worker selections keep the explicitly chosen account and the worker’s saved model and reasoning. The daemon enforces the frozen worker selection and concurrency limit. Provider defaults have no worker picker; saving them preserves existing inherited teams on individual profiles. Explicit installation worker accounts require support from every environment. Recursive worker presets are rejected. These controls coordinate managed agents; they are not a filesystem sandbox or a limit on native provider subagents. See [supervision](agent-presets.md#supervision).
- **Inspectable compaction summaries.** Expand each completed compaction marker to read, copy or export its saved summary without a model call. Supported adapters retain provider text, available context token counts and Pi's retained-entry boundary; estimates are labeled. Claude summaries come from matching transcript boundaries, Pi and OMP from completion results, and OpenCode from summary records. Codex events currently expose no readable summary. Older events without saved text explain the absence. Summaries are only part of the next model request. This requires the updated daemon to capture new artifacts; previously stored markers are not backfilled. See the [inspector](../packages/app/src/compaction/marker.tsx) and [browser checks](../packages/app/src/compaction/marker.browser.test.tsx).
- **Codex goal controls.** Set an objective with an optional token budget, inspect status, elapsed time and measured token usage, and pause, resume or clear it. Vorteo connects the interface and daemon to Codex's native goal lifecycle, reconciles notifications with reads, and coordinates attached context with goal activation. Token consumption is not a measure of task completion. A provider-independent goal lifecycle remains planned. See the [goal adapter](../packages/server/src/server/agent/providers/codex/goals.ts) and [goal presentation tests](../packages/app/src/goals/goal-presentation.test.ts).
- **Durable queues shared across devices.** Queue messages with files or images, edit or reorder them from another connected client, and let the daemon deliver them with all clients closed. Saved queues survive service recreation. Interrupted delivery is reconciled rather than blindly replayed; a durable queue does not guarantee uninterrupted execution of a provider turn through a restart. See [queue service tests](../packages/server/src/server/message-queue/service.test.ts).
- **Quota stops and schedule admission.** Structured quota exhaustion pauses affected tasks, prevents subsequent turns and managed-worker creation, cancels active managed teammates and suppresses completion wakeups. Schedule admission also checks quota. Recovery uses a confirmed reset or a reviewed successor; transport failures do not establish exhaustion. Configurable reserve thresholds remain incomplete, as described below. See [quota behavior](agent-presets.md#quota-stops-and-explicit-successors).
- **Workers stay with their task.** Managed workers remain beneath their originating task and project even when executing in isolated worktrees. Independent follow-up chats, terminals and scripts stay accessible in the worker workspace. Separate unpublished refinements display profile codes, models and reasoning, show native provider configuration when available, and let users hide finished native workers locally. See [agent lifecycle](agent-lifecycle.md) and [worker presentation](../packages/app/src/subagents/track-presentation.ts).
- **Separate queue and goal controls.** Pausing queue delivery leaves an active goal eligible to continue; stopping the task pauses both. Queue delivery can temporarily hold goal continuation and release it after queued work finishes. Reconnection requires confirmed goal state before allowing changes. See [queue and goal tests](../packages/server/src/server/message-queue/goal-hold.test.ts).
- **Recoverable local queue edits.** Unsaved text and attachment edits survive reloads on the device where they were made. Save synchronizes the edit; Cancel retains the shared message. Messages awaiting synchronization use ordinary queue rows with a waiting indicator and a “Queued on this device” tooltip. Stale edits and interrupted submissions require reconciliation. See [draft recovery tests](../packages/app/src/message-queue/edit-draft-session.test.ts).

## Execution environments and installation

- **Automated upgrade restarts that wait for idle.** After preparing release files, queue an owner-approved restart of the Host or Dev container daemon. The coordinator persists approval, waits for running agents, initializing sessions and native workers, and dispatches automatically with the browser closed. A final daemon-side idle check closes admission before restart; cancellation remains available before dispatch. This automates the restart step, not release preparation, and does not provide zero downtime: the daemon becomes briefly unavailable and terminals may disconnect. Installation controls show the requested change, waiting time and history. Owners can also hold new work, let current turns finish, and restart after draining; canceling the hold retains goal intent. Sidebar restart notices name the Host or Dev daemon, distinguish queued and restarting states, and keep their top divider fixed while messages scroll. See [restart and recovery](execution-installation.md#restart-and-recovery) and [idle restart tests](../packages/server/src/server/execution-installation/restarts.test.ts).
- **Container installation with private HTTPS.** The installer builds the application, creates private storage and starts a development container with Tailscale access and application authentication. Agents can modify mounted projects and container storage; unmounted host files remain outside their filesystem access. New builds include Chromium libraries and fonts for browser testing. Connect additional devices through Tailscale with the environment address and existing authentication; QR and pairing-link onboarding are retired. See the [container installer](../docker/multiplex/README.md), [security boundaries](container-tailscale.md) and [browser setup](development.md#chromium-in-the-development-container).
- **Host and Dev container in one installation.** An explicitly authorized macOS host extension adds a native daemon and protected interface alongside the existing container. Choose the execution environment with the account and profile. Host runtime, state and credentials stay outside guest-writable mounts. Native agents run with the owner's host authority; this is not equivalent to container confinement. See [host and container execution](execution-installation.md).
- **Shared installation settings.** Provider policy, instructions, metadata preferences, terminal definitions, skills, plugins and browser-tool defaults share installation authority. Environment exceptions preserve local credentials, paths and connections. Removing one local connection retains its shared definition and other connections. Disconnected environments reconcile shared configuration on reconnect. See [shared profile authority](agent-presets.md#profiles-across-execution-environments).
- **Protected owner access and restart validation.** A separate generated owner password unlocks installation controls for seven days per browser, with explicit locking and persisted token hashes. Each restart still requires approval. Host startup validation checks the configured release before dispatch and reports failures without exposing configuration values. Pending requests remain visible; completed and rejected requests stay in history. See [restart and recovery](execution-installation.md#restart-and-recovery).
- **Host orchestration of container workers.** Trusted host orchestrators can manage agents through the coordinator's fixed container-management interface. Container credentials cannot use that interface to approve restarts or obtain host-shell authority. See [agent management](execution-installation.md#agent-management).
- **Private workspace previews and host folders.** Workspace services reuse the task's existing workspace, configured service and HTTPS reservation. Shared host folders are explicit mounts, and preview registration does not authorize broader host access or duplicate workspaces. See [preview workspace reuse](../docker/tailscale/AGENT-INSTRUCTIONS.md#preview-workspace-reuse).
- **Optional private custom domains.** A separate Tailscale and Caddy gateway gives the application a custom HTTPS hostname without publishing host ports or enabling Funnel. DNS validation renews certificates, and application authentication remains required. See [private domains](private-domain.md).
- **Installation update workflows.** Source update checks prepare editable update and upstream-merge tasks. Persistent publication uses guarded builds and receipts; a web-only update cannot activate new daemon behavior. Installation connections survive reloads and domain migration. See [instance continuity](instance-continuity.md).

## Skills and instruction management

- **Shared skill library.** Settings exposes installed skills across environments with instruction content, ownership, hashes, provenance and audit export. Shared provider discovery paths appear once per environment, with each path retained in Details. See [skill library](skill-library.md).
- **Reviewed skill changes.** Preview pinned installation, provider discovery links, identical-copy consolidation, removal and restoration before applying them. Backups and conflict checks protect local edits. Managed installations keep a canonical catalog and project reviewed definitions into each environment. See [skill operations](skill-library.md).
- **Profile skill selection.** Profiles can inherit defaults with exclusions, select specific packages or disable optional skills. Supported Claude and Codex runtimes freeze restricted selections for each task; unsupported restrictions fail rather than claiming enforcement. Selection limits discovery and invocation, not filesystem or tool access. See [profile policies](skill-library.md#profile-policies).
- **Environment exclusions.** Disable a personal skill for one environment while retaining its shared definition and installed files. New tasks obey current installation policy; a profile cannot override an environment exclusion. Existing tasks retain their recorded selection. See [environment exceptions](skill-library.md#environment-exceptions).

## Projects, devices and interface

- **PR merge activity in the sidebar.** The existing second-line PR link shows Awaiting merge when GitHub reports auto-merge or actual merge-queue membership, and Merging while a merge submitted through this client is pending. Confirmed merged or closed state takes precedence. Shell commands and merges submitted from other clients do not establish local pending activity. Missing or invalid facts retain the ordinary PR display.

- **Tasks across environments in one workspace.** New task drafts select Host or Dev container independently of the account and profile. Text and uploaded files survive switching; uploads transfer on submission with size and provenance checks. Exact directory mappings retain worktree paths, and persisted companion associations remember a chosen folder. Tabs route actions and subscriptions to their task daemon, retain associations through reload and hydration, and show environment icons. Archives include companion workspaces after connection and protection preflight. Workspace and plugin references require removal or switching back. Both daemons must advertise `workspaceTaskEnvironments`; existing conversation handoff remains separately reviewed. See [host and container execution](execution-installation.md).

- **Enclaves for ongoing work.** The collapsible Standing section contains workspaces with archive protection or an active or paused schedule targeting one of their unarchived threads. Standing is derived, with no manual toggle. Its heading aligns with workspace dots, uses the workspace title size and shows a count badge only when collapsed. The icon-free row has a leading disclosure arrow and a full-width hover highlight. Paused appears when all remaining schedules are paused; any active schedule shows Scheduled. Completed or expired schedules do not keep a workspace in Standing. Protected blocks workspace, chat and project archives until explicitly removed. Tag As shows schedule management, protection and the custom label catalog, including existing reserved-name labels marked as custom. Creating a workspace schedule asks for a thread when several are available, then a prompt and cadence; it does not run immediately. Removing the final schedule removes Standing membership unless protection remains. Existing server lifecycle fields remain wire-compatible. Startup migration of legacy Protected labels remains supported. Compact badges match activity counters, and sidebar menus overlay trailing content without shifting the row.
- **Environment-aware project organization.** Projects can group workspaces from different environments and repositories. Move a workspace and all its chats to another project through its menu or drag and drop on web and desktop, preserving history, environment and working directory. Profile handoffs can select or create a destination workspace without losing the project context. Explicitly moved worker workspaces retain their chosen project, and empty projects remain visible on older daemons. Updated daemons are required for project moves.
- **Responsive profile selection.** Environment, account and profile selection uses three desktop cards or collapsible mobile sections. Profiles display saved model and reasoning settings, permissions and worker details. The chooser opens immediately while data loads, adapts its profile grid to available width, and respects reduced-motion preferences.
- **Touch access and Home Screen behavior.** Sidebar actions and workspace diff controls retain usable touch targets on phones, tablets and narrow windows. iOS Home Screen layouts account for the viewport and suppress the native top blur in newly installed shortcuts. Older shortcuts can retain installation metadata and need replacement. See [touch behavior](vorton-touch-audit.md) and [Home Screen troubleshooting](ios-home-screen.md).
- **Conversation readability.** Web and desktop timelines preserve surrounding text as image sizes settle during history scrolling. Question, approval, plan, queue, goal and subagent cards share compact spacing and borders. The Subagents heading collapses its contents while leaving the count and Archive finished action accessible.
- **Task visibility and navigation.** Sidebar activity badges show queued messages, managed workers and active goals, with a visibility preference. Search, History, Schedules and Settings remain accessible; configured search shortcuts appear in the tooltip. Archiving a workspace returns to the empty New workspace page. Usage stays beside account selection rather than in the sidebar.
- **Unified settings navigation.** One installation navigation exposes shared settings and environment exceptions. Environment tabs stay visible above scrolling details. Settings tabs use a full-width baseline and rounded top corners. Agent profiles shows one provider family at a time; defaults use an available account catalog and provider-discovered skills. Navigation starts with General, Environments, Providers and Agent profiles; editor preferences explain Vim modes and basic commands.
- **File downloads.** Binary previews offer a visible Download button, including files opened from conversation links.

## Product identity and release tracking

- **Vorteo identity.** App names, icons and packaging identify the fork. There is no alternate Paseo mode or separately installed Paseo application; install upstream independently to use both.
- **Custom release history.** What's new combines bundled Vorteo notes with Paseo notes in date order, labels their source and loads older entries automatically while scrolling. Custom notes remain available when the upstream feed cannot be reached. Full changelog opens the Vorteo history on GitHub. Commit hooks require a staged, dated entry for every commit, including maintenance. See [release notes](release.md#vorteo-release-notes).
- **Continuous custom versions.** Each commit advances the Vorteo counter, including documentation and tooling commits. Upstream upgrades retain that sequence; manifests, internal dependency pins, lockfiles and native metadata stay synchronized through the installed hook. See [commit versioning](release.md#vorton-commit-versions).

## Incomplete integrations

- **Quota reserve controls.** The daemon includes policy validation, frozen launch policy, admission, usage observation, persistence and restart reconciliation. The app still needs reserve controls, launch-policy selection, capability integration and end-to-end acceptance. Do not advertise Cruise Reserve or Redline as an available user workflow. See [implementation status](agent-presets.md#implementation-and-deployment-status).
- **Acceptance across installations and devices.** Native host setup, real account sign-in, supervisor/Pi workflows, physical devices, dictation, accessibility and performance require environment-specific acceptance. A source test or responsive browser layout does not establish those results. See [host acceptance](host-handoff.md#acceptance). Keep deployment evidence private.

## Upstream comparison

Reviewed on October 7, 2026 against integrated Paseo commit `c062280429c2aa894d98ce8d5c8a270c519085c8` from the `0.11.0-beta.3` line. This is the integrated baseline, not a claim about the latest upstream release. The [upstream changelog](../CHANGELOG.md) records the inherited changes.

- **Usage visibility has partial overlap.** Paseo provides per-subscription usage discovery across coding tools, custom credential-home support, plugin usage sources and pinned windows. Those are inherited capabilities. Vorteo retains its account connection workflows, usage in profile selection, reset-credit management and quota lifecycle. Usage visibility by itself is no longer a fork differentiator.
- **Provider configuration and plugins have partial overlap.** Paseo provides provider option defaults, command and environment overrides, plugin settings and registry support, plus Antigravity and Muse Code integrations. Vorteo adds its shared workflow authority, account management, environment exclusions and bounded worker-profile launches. The provider integrations themselves are upstream work.
- **Mobile operation has partial overlap.** Paseo provides mobile clients, tablet terminal controls and ongoing keyboard and layout improvements. Vorteo's remaining customizations include its environment/account/profile chooser, shared durable queue workflow, task activity badges and Home Screen adjustments. Mobile access itself is inherited.
- **Skill deduplication has partial overlap.** Paseo fixed duplicate discovery of its own skills in Codex. Vorteo additionally provides a shared inventory, provenance, reviewed package operations, environment policy and frozen profile selections. The upstream fix does not establish parity with the library workflow.

No complete replacement of these custom workflows was established in this review. Future upstream merges must reassess behavior and tests, narrow the inventory to remaining differences, and update the roadmap under the [maintenance rules](writing.md#maintain-the-vorteo-customizations-inventory).
