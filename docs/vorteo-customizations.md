# Vorteo customizations beyond Paseo

Vorteo extends Paseo with account management, reusable workflows, supervised workers and a shared Host and Dev container installation. This is the cumulative inventory of those differences, grouped by category and ordered by user impact within each category. Minor interface changes belong here rather than in the product overview.

This inventory describes the reviewed source. Availability depends on the installed client, daemon, coordinator and provider versions; source review does not establish deployment. The [roadmap](roadmap.md) tracks unfinished work, [Vorteo changelog](../VORTEO_CHANGELOG.md) records release history, and linked guides explain operation and constraints.

Worker visibility maintenance: retained worker conversations remain available in their native execution workspaces as well as the parent presentation. Explicit execution-workspace tabs stay there. Focused coverage includes both workspace descriptors, archived workers, parent grouping and automatic opening from an empty workspace. Factory worker archival remains an owner action; configurable automatic cleanup is deferred.

## Accounts and reusable workflows

- **Multiple isolated subscription accounts.** Connect separate Codex and Claude accounts, choose an account per task, and run tasks across accounts concurrently. Browser sign-in, reconnect, rename, disable and removal are account-scoped. Claude uses the official CLI setup-token flow; managed installations deliver one subscription credential to Host and Dev, subject to explicit exclusions. Account configuration, session discovery and resumed history remain isolated. Setup-token usage and reset credits are unavailable; reconnect renews the process credential without a private refresh API. Source delivery and live subscription acceptance remain pending. See [Claude subscription connections](providers.md#claude-subscription-connections). Connection controls honor its account-scoped CLI authentication check even when macOS saved credentials are unavailable to usage reporting; explicit authentication rejection still offers Reconnect. This does not combine subscription allowances or automatically fail over between accounts. See [accounts and profiles](agent-presets.md) and [account isolation tests](../packages/server/src/server/agent/providers/claude/account-isolation.test.ts).
- **Reusable launch profiles.** Save model, reasoning, permissions, instructions, provider features and worker settings together. The daemon resolves the selected profile and freezes its launch configuration for the task. Later profile edits affect new tasks. Unsupported model or reasoning choices fail explicitly instead of silently selecting another model. See [launch configuration](agent-presets.md#configuration-and-compatibility) and [profile tests](../packages/server/src/server/agent/create-agent/profile.test.ts).
- **Shared workflows across accounts and environments.** Provider defaults and named workflows avoid maintaining a separate copy for each account. Managed installations keep one authoritative profile library across Host and Dev container, with explicit environment exclusions and revision checks for edits. Discovered models stay local. Claude setup-token connections synchronize through the installation coordinator; other provider authentication retains its existing behavior. New-task drafts use the same Environment, Account and Profile chooser, with three desktop columns and compact sections. Profiles have an account-independent identity, retain compatible selections when switching accounts, and hide incompatible choices after catalog discovery. Legacy launch and worker references survive migration. See [profiles across execution environments](agent-presets.md#profiles-across-execution-environments).
- **Reviewed task handoffs.** Changing the profile on an existing task opens an editable context handoff and creates a successor after confirmation. The original remains accessible. Choose the destination workspace when changing environments; the project stays selected. Active managed workers must stop first. Attachments, tool results and provider-private state do not transfer automatically. See [successors and quota stops](agent-presets.md#quota-stops-and-explicit-successors).
- **Usage beside account selection.** Remaining usage, reset windows and a compact usage ring help choose an account before launching work. When a coding allowance reaches zero and prepaid credit remains, account tiles show the balance in amber with Using prepaid and retain the reset time. Cached balances are marked as last known. Reset buttons keep gray text at every quota level. Drafts restore their account and workflow together. Fresh capacity can inform successor suggestions; stale or unknown usage does not qualify as available capacity. Paseo also supplies usage discovery and plugin sources, credited below.
- **Account reset credits.** Supported providers expose account-scoped credit availability and a reviewed reset operation. The picker loads credits for enabled account connections even when shared profiles name only the provider family. Credit details include reported expiry and refresh time; redemption requires explicit confirmation and verified provider support. A confirmed reset unlocks earlier quota-exhausted threads on that provider without automatically sending a message or clearing a reserve stop. See [reset credits](agent-presets.md#account-reset-credits).
- **Local Pi endpoint visibility.** Profiles show configured model and reasoning details, private endpoint reachability and active managed-child counts. A reachable port does not prove a loaded model, valid authentication or inference capacity. Counts describe the configured provider in this daemon. See [local endpoint status](agent-presets.md#local-endpoint-status).
- **Provider management and diagnostics.** Settings groups each provider family with its accounts and shared enable controls. Reorder, remove or restore providers without deleting credentials, profiles or history; local sign-in and credential deletion remain in Manage. Account names use the same natural order across environments. Older Claude CLI versions show installed-version and model-compatibility warnings with update guidance. A separate unpublished refinement shows sign-in success and Done independently of background usage refresh.

## Goals, queues and supervised workers

- **Resizable conversation columns.** At 1,080 CSS pixels of primary-region width, text and task cards occupy separate columns above the composer. Text aims for the full region's center, aligned with the composer, and shifts left only to preserve a 32px gap from the cards. The right inset and card spacing are both 16px. Cards can be dragged as narrow as 220px. Open cards share the available height; short cards stop at their content height and long bodies scroll internally. Opening, closing and resizing cards uses short exponential easing and honors reduced motion. The web conversation hides its scrollbar and scroll edges fade only where content continues, using the existing scroll measurements so retained tabs preserve reading positions. Hover handles resize cards from their left edge and text from its right edge. Preferred widths persist independently of the composer width and are temporarily clamped when sidebars reduce the available space. Below the threshold, cards return to the conversation footer. Cards appear in Goal, Tasks, Journal, Subagents, Messages order in both layouts; action permission prompts follow them. Questions stay in the left conversation column. Native touch resizing and card transitions still need physical-device acceptance. Implementation: [column layout](../packages/app/src/agent-stream/columns/layout.tsx).

- **Thread journals.** Agents record critical decisions and verified progress with `append_journal` and read them with `get_journal`. Each thread has an append-only journal accordion with small local timestamps beside selectable entry text. Entries keep their server append order across reloads, retries and clock changes. A repeated entry ID with identical text returns the saved entry; different text is rejected. The card appears after the first entry, shares the conversation heading and hover design, and keeps its header visible while its bounded body scrolls. Archived threads retain read access. This requires the daemon's `agentJournal` capability; Clear journal clears the current device's card through its latest observed entry without deleting history; Show history restores it, and new entries remain visible. Clear state is scoped by environment and thread and survives reload. Seen entries are tracked separately on each device by environment, thread and entry ID. Unread entries use red four-point Spark markers joined by dark gray lines beside the timestamps. After an entry’s timestamp stays visible for 800ms in the active window, its Spark contracts with a faint halo into a gray dot over 450ms. Reduced motion skips the transition. Collapsed, background and offscreen entries remain unread; the header counts the visible history’s unread entries. Storage failures retain unread state and offer Retry. Native visibility measures the card viewport and still needs physical-device acceptance. There are no entry editing, deletion or reordering controls.

Sidebar rows omit the goal badge. Their sub-agent badge counts managed workers with open turns and running provider workers, and disappears at zero; finished unarchived workers remain in their task cards. Browser coverage checks the accessible count text and its disappearance after a turn finishes.

- **Thread checklists and workspace progress.** Each thread shows its checklist accordion after its first task exists and hides it again when empty. A Clear completed header action deletes completed editable tasks and their dependency links using guarded writes; pending, active and provider-owned tasks remain. Partial cleanup errors are visible and can be retried. Task heading count badges separate completed and total counts with a spaced slash. Tasks use one row with a left reorder handle, a completion checkbox and a trailing edit pencil; owner and dependency details remain in the editor. Blocked tasks use a neutral Lucide CircleAlert icon in checklist cards and compact task rows, retaining their existing control colors and Blocked badge. Active task rows use a foreground outline spinner driven by the shared status-ring clock, with no center dot; their completion controls remain usable. Checklist items are progress records, not queued agent turns. Unfinished items do not block restart readiness or bypass a finish-turns hold; a focused regression covers edits during the hold. The sidebar flower sums tasks across all unarchived threads in its workspace, including unopened threads, and sits after labels and badges, yielding the far-right edge to hover or touch row actions. Sidebar and card headers share slim rounded SVG petals: green complete, blue active, gray pending. Up to twelve tasks get individual petals; larger totals use twelve proportional petals, rounding completion down and reserving one blue activity signal when work is active. Hover and keyboard focus expose exact completion and active counts. One task uses a centered upright petal. One to three tasks use wider, fuller petals; two and three tasks have a smaller center gap. The active-count tooltip uses English fallback in other locales. Provider-independent `get_checklist` and `update_checklist` tools let agents create, inspect, update, complete, reopen, delete and reorder their own thread's tasks. Tasks retain stable IDs, completion criteria, progress labels, assignment labels, dependencies and metadata. Agents can set and clear a distinct blocked status with or without dependencies. Blocked items remain incomplete, persist through reloads and show a badge in task rows; the editor offers the status on capable daemons. Older clients receive an incomplete pending representation. Dependencies prevent starting or completing tasks with unfinished prerequisites; deletion clears dependency references. Manual controls support the same task lifecycle, descriptive fields, assignment, prerequisites and ordering, with stale-edit checks and visible save errors. Metadata remains available through the agent tools. Native provider tasks remain visible and use their provider's writer, avoiding conflicting ownership. Claude task snapshots retain details and dependency updates through list refreshes and ignore failed writes. Durable writes precede broadcasts, survive reloads and resist stale history or projection writes. Planning and handoff instructions carry pending accepted items, completion criteria, dependencies and existing authorization into implementation threads. Tool access remains caller-thread scoped and subject to existing policy. Older daemons keep read-only native cards; managed controls require the advertised checklist capability. This source expansion requires updated daemons and interface; installation acceptance is pending. See [checklist model](../packages/server/src/server/agent/task-checklist/model.ts), [agent tools](../packages/server/src/server/agent/task-checklist/tools.ts) and [browser acceptance](../packages/app/e2e/browser/scrolling-agent-cards.spec.ts). Blocked tags show the recorded task description on hover, keyboard focus or touch; legacy tasks without a reason explicitly say so. Agents are instructed to reassess blockers on continuation and relevant state changes. An updated daemon also reviews eligible idle threads after an hour without activity or a previous review. Reviews reuse the retained session, preserve queued messages and goal identity, and respect manual pauses, exhausted budgets, pending delivery, restart holds and newer owner actions. Archived, internal, delegated and controller-owned threads are excluded. The persisted cooldown survives daemon reloads; a concurrently archived thread cannot enter review.
- **Bounded worker teams.** Sub-agent card rows use one line without dividers, placing profile/model/effort metadata before the right-edge actions. Narrow layouts truncate text while preserving action space. A supervisor profile explicitly selects a worker account and profile, including cross-provider delegation, and limits concurrent managed workers, including Pi workers using local or private OpenAI-compatible endpoints. Existing teams retain their account binding until edited; new worker selections keep the explicitly chosen account and the worker’s saved model and reasoning. The daemon enforces the frozen worker selection and concurrency limit. Provider defaults have no worker picker; saving them preserves existing inherited teams on individual profiles. Explicit installation worker accounts require support from every environment. Recursive worker presets are rejected. These controls coordinate managed agents; they are not a filesystem sandbox or a limit on native provider subagents. See [supervision](agent-presets.md#supervision).
- **Inspectable compaction summaries.** Expand each completed compaction marker to read, copy or export its saved summary without a model call. Supported adapters retain provider text, available context token counts and Pi's retained-entry boundary; estimates are labeled. Claude summaries come from matching transcript boundaries, Pi and OMP from completion results, and OpenCode from summary records. Codex events currently expose no readable summary. Older events without saved text explain the absence. Summaries are only part of the next model request. This requires the updated daemon to capture new artifacts; previously stored markers are not backfilled. See the [inspector](../packages/app/src/compaction/marker.tsx) and [browser checks](../packages/app/src/compaction/marker.browser.test.tsx).
- **Codex goal controls.** Set an objective with an optional token budget, inspect status, elapsed time and measured token usage, and pause, resume or clear it. Vorteo connects the interface and daemon to Codex's native goal lifecycle, reconciles notifications with reads, and coordinates attached context with goal activation. Vorteo adds current-thread goal read and edit tools, including objective changes and authorized resumption of blocked work. Edits compare the observed goal under the same lock as owner and queue mutations; budgets and usage remain intact. The agent cannot select another thread, revive completed or limited goals, or edit through a restart or queue hold. This extension is implemented in source and awaits installation acceptance. Token consumption is not a measure of task completion. A provider-independent goal lifecycle remains planned. See the [goal adapter](../packages/server/src/server/agent/providers/codex/goals.ts) and [goal presentation tests](../packages/app/src/goals/goal-presentation.test.ts).
- **Stable asynchronous reordering.** Tasks, Messages and provider settings retain the dropped order until authoritative data changes, without returning to their starting positions while saving. Shared web/native handling preserves current row content and rolls back failed saves; rejected or uncertain queue operations retain recovery controls. Tasks and Messages omit routine reorder status. Sidebar and workspace tabs already update local order synchronously. Desktop and phone browser checks cover delayed saves and rejected mouse drops; native gesture behavior still needs device verification.
- **Durable queues shared across devices.** Queue messages with files or images, edit or reorder them from another connected client, and let the daemon deliver them with all clients closed. Saved queues survive service recreation. Recovery controls stay inside the Messages card even after the last message leaves. Send now waits for pending delivery and local queue operations. A fresh server snapshot retires rejected send-only controls whose target is gone, including retained copies; message content, edits, attachments and uncertain delivery remain available for review. Interrupted delivery is reconciled rather than blindly replayed; a durable queue does not guarantee uninterrupted execution of a provider turn through a restart. See [queue service tests](../packages/server/src/server/message-queue/service.test.ts).
- **Quota stops and schedule admission.** Structured quota exhaustion pauses affected tasks, prevents subsequent turns and managed-worker creation, cancels active managed teammates and suppresses completion wakeups. Schedule admission also checks quota. Recovery uses a confirmed reset or a reviewed successor; transport failures do not establish exhaustion. Configurable reserve thresholds remain incomplete, as described below. See [quota behavior](agent-presets.md#quota-stops-and-explicit-successors).
- **Workers stay with their task.** Managed workers remain beneath their originating task and project even when executing in isolated worktrees. Independent follow-up chats, terminals and scripts stay accessible in the worker workspace. The subagent list separates Vorteo workers from provider subagents and explains their ownership. Provider children show lifecycle status, use “Model not reported” when metadata is absent, and have a dismissal control that hides finished children until the app reloads without archiving their sessions. Clear finished archives managed workers and dismisses provider children. These presentation changes do not enforce worker profiles or concurrency limits on provider-native delegation. New explanation keys use English fallback in other locales. See [agent lifecycle](agent-lifecycle.md) and [worker presentation](../packages/app/src/subagents/track-presentation.ts).
- **Separate queue and goal controls.** Pausing queue delivery leaves an active goal eligible to continue; stopping the task pauses both. Queue delivery can temporarily hold goal continuation and release it after queued work finishes. The goal card explains this as a smaller parenthesized waiting status and shows when continuation is automatic. Goal time is labeled; pause help explains that pausing disables automatic continuation. Compact layouts keep Edit and Pause in the heading and place goal time and Clear goal in the expanded card. Message delivery failures replace the waiting explanation with the reason and a review action that opens the queued messages card. Uncertain delivery warns that retrying may duplicate the message. Reconnection requires confirmed goal state before allowing changes. See [queue and goal tests](../packages/server/src/server/message-queue/goal-hold.test.ts).
- **Recoverable local queue edits.** Unsaved text and attachment edits survive reloads on the device where they were made. Save synchronizes the edit; Cancel retains the shared message. Messages awaiting synchronization use ordinary queue rows with a waiting indicator and a “Queued on this device” tooltip. Stale edits and interrupted submissions require reconciliation. See [draft recovery tests](../packages/app/src/message-queue/edit-draft-session.test.ts).

## Execution environments and installation

- **Reviewed Factory startup adoption.** A separate Host-requested Installation operation binds approval to a protected startup plan, keeps cancellation visible, stages the reviewed source and verifies the replacement Dev worker. It cannot inherit automatic Host approval or a plain restart's approval. Coordinator maintenance binds configuration changes to its exact reviewed plan. Failed adoption fences later lifecycle work until a separately approved linked recovery verifies the selection. Trusted startup can select the retained accounting directory without moving the daemon home or opening a second ledger. Deployment, private controller wiring and operating-loop acceptance remain separate. See [Factory startup adoption](execution-installation.md#tracked-factory-startup-adoption).

Source batching preserves complete historical release-note entries, including duplicate counts, across interleaved integrations. Historical edits and deletions remain blocked. Coordinator recovery retries pending conflict validation without transferring approval or replaying installation; the sidebar distinguishes correction, validation, waiting and approval states.

- **Coordinator emergency recovery.** Exact coordinator plans can include one automatic restoration of the previous release. An independent macOS watchdog bounds a stalled stage, fences only the recorded updater with a PID-version audit token, then acquires the existing lifecycle lock. Recovery verifies the selected service, rollback artifact and preserved state, including the exact loaded arguments of an already exited candidate, records its outcome, and never replays the update or an interrupted rollback. Requires compatible installed runner and Host review support.

- **Trusted Host restart policy.** The trusted Host restart policy is implemented in source but still awaits coordinator bootstrap and live acceptance. It automatically approves authenticated Host requests through the existing graceful lifecycle, keeps Dev and mixed-origin batches under manual review, and records exact approval provenance. See [policy and installation limits](execution-installation.md#trusted-host-approval-policy). The [bootstrap design](plans/execution-environments/coordinator-maintenance.md) defines the remaining owner authentication, exclusive handoff and recovery acceptance work; it is not an installed capability. The v226 integration preserves the concurrently published environment-selector persistence and worker-workspace visibility fixes.

- **Automated upgrade restarts that wait for idle.** After preparing release files, queue an owner-approved restart of the Host or Dev container daemon. The coordinator persists approval, waits for running agents, initializing sessions and native workers, and dispatches automatically with the browser closed. A final daemon-side idle check closes admission before restart; cancellation remains available before dispatch. This automates the restart step, not release preparation, and does not provide zero downtime: the daemon becomes briefly unavailable and terminals may disconnect. Installation controls show the requested change, waiting time and history. Owners can also hold new work, let current turns finish, and restart after draining; canceling the hold retains goal intent. Both restart targets remain visible together. Pending cards offer Restart when idle, Finish turns and restart, and Cancel; queued cards offer Cancel and Restart appears stuck. Force restart now appears only after the operator reports the queued restart stuck and still requires interruption confirmation. Sidebar notices only offer review. Later plain requesters share an existing plain restart approval. Source updates require the separate exact-source approval below. See [restart and recovery](execution-installation.md#restart-and-recovery) and [idle restart tests](../packages/server/src/server/execution-installation/restarts.test.ts).
- **Container installation with private HTTPS.** The installer builds the application, creates private storage and starts a development container with Tailscale access and application authentication. Agents can modify mounted projects and container storage; unmounted host files remain outside their filesystem access. New builds include Chromium libraries and fonts for browser testing. Managed installations welcome new devices with one owner-password field and register Host and Dev together. Standalone clients retain direct server connections; QR and pairing-link onboarding are retired. See the [container installer](../docker/multiplex/README.md), [security boundaries](container-tailscale.md) and [browser setup](development.md#chromium-in-the-development-container).
- **Host and Dev container in one installation.** An explicitly authorized macOS host extension adds a native daemon and protected interface alongside the existing container. Choose the execution environment with the account and profile. Host runtime, state and credentials stay outside guest-writable mounts. Native agents run with the owner's host authority; this is not equivalent to container confinement. See [host and container execution](execution-installation.md). Paired Linux managed workers recover a missing client-path environment variable from their validated private pairing client, retaining exact installation admission checks. This repair can use a managed worker update without replacing its supervisor.
- **Shared installation settings.** Provider policy, instructions, metadata preferences, terminal definitions, skills, plugins and browser-tool defaults share installation authority. Environment exceptions preserve local credentials, paths and connections. Removing one local connection retains its shared definition and other connections. Disconnected environments reconcile shared configuration on reconnect. Enabled Codex and Claude account definitions with a missing environment binding remain pending unless explicitly excluded, while unrelated settings continue applying. This checks binding completeness only; installation-wide authentication and refresh synchronization remain in progress. See [shared profile authority](agent-presets.md#profiles-across-execution-environments).
- **Reviewed source updates.** Dev can upload committed integration source without executing it. Pending unapproved submissions combine into one commit with contribution receipts and provenance. Submissions that already include the accepted source preserve their reviewed tree; divergent submissions still undergo conflict checks. Review shows one short paragraph, with source details and superseded submissions collapsed. Finish-current-turns holds recover goals and ordinary thread continuations across daemon replacement while preserving manual pauses. Conflicts stay queued for the requesting agent to repair; the review explains that owners can wait or cancel an unwanted update. Coordinator and daemon sidebar reviews use compact shared actions. approved batches freeze and later submissions form the next batch. Owner approval binds the final source revision, bundle digest and batch revision before Host builds native dependencies, replaces its daemon and publishes the guarded interface. Batching requires the updated coordinator and interface. Setup pins coordinator tooling separately from the selected runtime. Dev runtime updates use a separate target batch and approval, build native dependencies inside the configured container, retain its supervisor and verify the replacement executable. Capability discovery reports bootstrap blockers. The Host installer pins the container, preserves configuration and refreshes guest request tooling. Existing installations require bootstrap and live acceptance. Idle installation and coordinator or supervisor self-update remain excluded. See [reviewed source updates](execution-installation.md#reviewed-source-updates).
- **Protected owner access and restart validation.** A separate generated owner password unlocks installation controls for seven days per browser, with explicit locking and persisted token hashes. Each restart still requires approval. Host startup validation checks the configured release before dispatch and reports failures without exposing configuration values. Pending requests remain visible; completed and rejected requests stay in history. See [restart and recovery](execution-installation.md#restart-and-recovery).
- **Host orchestration of container workers.** Trusted host orchestrators can manage agents through the coordinator's fixed container-management interface. Container credentials cannot use that interface to approve restarts or obtain host-shell authority. See [agent management](execution-installation.md#agent-management).
- **Private workspace previews and host folders.** Workspace services reuse the task's existing workspace, configured service and HTTPS reservation. Sidebar preview globes use a neutral color and a four-pixel right inset; service health remains in the accessible label. Administrators can enable bounded recovery after daemon restarts for active, unchanged, previously verified services. Recovery rechecks listener ownership and TLS; explicit stops remain stopped. Shared host folders are explicit mounts, and preview registration does not authorize broader host access or duplicate workspaces. See [preview workspace reuse](../docker/tailscale/AGENT-INSTRUCTIONS.md#preview-workspace-reuse).
- **Optional private custom domains.** A separate Tailscale and Caddy gateway gives the application a custom HTTPS hostname without publishing host ports or enabling Funnel. DNS validation renews certificates, and application authentication remains required. See [private domains](private-domain.md).
- **Installation update workflows.** Source update checks prepare editable update and upstream-merge tasks. Persistent publication uses guarded builds and receipts; a web-only update cannot activate new daemon behavior. Installation connections survive reloads and domain migration. See [instance continuity](instance-continuity.md).
